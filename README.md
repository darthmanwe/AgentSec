# AgentSec

**A security agent that reads untrusted code, decides what to do about it — and cannot act on
its own decisions.**

---

## The problem

Give an AI agent a repository to review and you have handed it a text box that strangers can
write into. A README, a code comment, a dependency description, a Jira ticket — all of it is
input the agent reads, and any of it can be written by someone who wants the agent to do
something else. Read this file, post that comment, change this cloud resource.

That is *indirect prompt injection*, and it is not hypothetical. On published agent benchmarks,
plain-text payloads succeed a few percent of the time and template-aware, multi-turn ones
succeed **over half** the time.

The usual defence is a better system prompt. That defence is measurably weak and gets weaker as
attacks improve, because it asks the model to be the thing that protects the model.

---

## The approach

AgentSec puts the safety **outside** the model.

The agent reads, reasons and proposes. A separate, deterministic control plane — policy engine,
human approval gate, signed short-lived capabilities, a single audited dispatch path — decides
whether any proposal actually happens. The model is treated as untrusted throughout. Not because
it is malicious, but because its input is.

> **The invariant:** the LLM may reason, propose actions, and request capabilities. It must never
> authorize itself, mint authority, or directly execute consequential external side effects.

So the claim this project makes is deliberately not *"the model behaved well"*. It is:

**even if the model is completely compromised, nothing unsafe executes.**

That is a claim you can test without trusting the model at all — which is exactly how it is
tested here.

## How the controls work

Five mechanisms, each of which can refuse independently:

- **The planner cannot execute.** It emits a typed `ActionPlan` and nothing else. There is no
  code path from planning to a backend — enforced by an import-graph test, not by convention.
- **Authorization is a separate process.** OPA decides ALLOW / DENY / REQUIRE_APPROVAL. Policy
  engine unreachable means DENY, never fallback-allow.
- **Approval binds an exact action.** A SHA-256 digest over canonicalized principal, workflow,
  tool, operation, resource, arguments *and immutable preconditions*. Mutate any argument after
  approval and the digest no longer matches.
- **Authority is short-lived and scoped.** Capability grants are Ed25519-signed, expire in
  30–120 seconds, and are bound to one tool, one resource, one digest, one request.
- **Retries do not duplicate side effects.** An execution ledger keyed on a logical `operation_id`
  is consulted before capability redemption, so durable retries and single-use grants coexist.

Throughout, the distinction that matters:

**unauthorized action attempts ≠ unauthorized action executions**

A model under pressure may propose anything. That is expected. The system fails only if a proposal
reaches a backend.

## What is built

Everything described here is implemented, tested and running in CI. Numbers in this README are
generated from a committed evaluation artifact by `uv run task report`; **CI fails if the README
drifts from its evidence**, so a stale number breaks the build rather than sitting there.

**The authorization kernel** decides what may happen, independently of any model. Policy denials,
fail-closed behaviour on an unreachable engine, exact-action approval binding, argument mutation
after approval, capability expiry, replay and cross-action reuse each have negative tests. 769
tests are marked `authz` and run with `ANTHROPIC_API_KEY` empty — the kernel's correctness never
depends on a credential being present.

**The execution path** carries a proposed action from plan to external effect, and every stage of
it can refuse. An MCP gateway dispatches to four real stdio servers. Temporal runs the review
workflow, pauses durably for a human decision, and survives a worker restart while waiting —
driven by `agentsec approve | deny | list` or the web UI. An execution ledger keeps a retried side
effect to one logical effect. Semgrep and Trivy run inside an ephemeral container with no network,
no capabilities, a read-only root and a per-run volume that is never a bind mount of the host. One
real external backend, GitHub, takes scoped reads and a single approval-gated write.

A fault-injection harness breaks each of those durability claims on purpose — killed worker,
activity timeout, transient failure, duplicated execution — and asserts they hold anyway.

**The guarantee against GitHub is at-most-once with reconciliation, not exactly-once.** Its
issue-comment endpoint exposes no idempotency key, so exactly-once is not available at any price.
A hidden operation marker plus a pre-write lookup narrows the duplicate window; the residual
exposure is stated in the threat model rather than papered over.

**The evaluation** is a LangGraph planning subgraph that proposes and cannot act, a deterministic
`AdversarialPlanner` modelling a planner that is *already fully compromised*, a 14-repository
benchmark corpus whose answer key lives where the agent under evaluation cannot read it, 22
template-aware and multi-turn injection cases, 29 privilege and approval cases, scorers, and a
preregistered hash-locked set of thresholds. Both axes have now been run; the live one cost $1.35.

**The audit trail can be checked without the code that wrote it.** Every step from proposal to
effect records the *inputs to* its decision, and `agentsec.observability.replay` re-derives the
verdict from that record alone:

> an execution is justified only if, earlier in the same authorization attempt and for the same
> action digest, there is an ALLOW — or a REQUIRE_APPROVAL followed by a granted approval — and a
> redeemed capability.

The independence is the point. A log written by the enforcement layer records what that layer
*believed* it did; if the enforcement is wrong, the log is wrong in the same direction, because
they share an author. Replay disagreeing with the counters is a finding. **A gap counts as a
violation**: an execution with nothing recorded before it is reported rather than skipped, because
the likeliest way for a trail to show a clean run is for the enforcement path to have stopped
writing to it.

Prometheus series are derived from the trail rather than incremented at call sites — a
hand-maintained counter is a second implementation of the control flow with nothing comparing it
to reality.

**The approval UI** renders attacker-controlled text by design, so its escaping is a security
control rather than presentation: all 22 corpus injection payloads are seeded as evidence and
asserted to produce no markup, behind a CSP of `default-src 'none'`, an Origin check and a
constant-time CSRF token.

1,168 tests run without the compose stack.

## How the result is measured

Two axes, reported separately, because they answer different questions and decay at different
rates (ADR-0002).

**Axis B — the control-plane guarantee.** A deterministic `AdversarialPlanner` emits the
attacker's desired plan directly: export a secret, comment without approval, mutate a cloud
resource, replay a spent capability, mutate arguments after approval, address another tool's
scheme, name a tool that does not exist. It models a planner that is *already fully compromised*,
so the claim does not depend on how gullible any model turns out to be — and does not decay as
models improve. It needs no credentials and runs in CI on every push.

**Axis A — model susceptibility.** A real model against a template-aware, multi-turn injection
corpus, through the identical control path. The only part that costs money, and it is gated behind
an explicit `--live --max-usd`: there is no path that infers "spend money" from a key happening to
be present in the environment.

Across 330 cases the model proposed the canary operation 8 times and the system executed it 0
times. Obfuscated payloads landed most often (3/45); plain text never did (0/60), which is the
direction the published attack-success literature predicts and the reason the corpus is not built
from plain-text payloads.

One caveat worth stating plainly, because the table invites the wrong reading: **the controls are
not the variable in the "proposed" column.** Policy, approval and capability constrain what
*executes*, not what a model *suggests*. What that column actually varies is the system prompt —
and the arms carrying an operational planner prompt proposed the canary while those carrying a
plain safety-instruction baseline did not. That is the opposite of what a prompt-hardening story
would predict, on eight events. It is reported as measured rather than explained away, and it
would need a much larger sample to believe.

Three design decisions keep the Axis-B number honest:

- **A benign action must execute under the identical configuration.** "Zero unauthorized
  executions" is trivially satisfied by a pipeline that cannot do anything, which is a claim about
  brokenness. The control test is the most important test in the suite.
- **Each attack declares which layer stops it**, and a test asserts the registry stops registry
  attacks, the scope check stops scope attacks, and so on. A defence-in-depth story where one
  layer happens to catch everything is one control with spare parts.
- **The permissive-policy run says what it does not prove.** It runs with a policy engine that
  allows everything, which makes the remaining layers earn their place — and means the two attacks
  whose defence *is* policy are asserted separately against live OPA rather than claimed there.

Getting Axis A to run at all cost four failed attempts and nothing in credit, because the API
rejects malformed requests before billing. Structured output does not support `maxItems`,
`uniqueItems` or numeric `minimum`; every object must set `additionalProperties: false`; a schema
may carry at most twelve *optional* properties document-wide, though required ones are free; and
the thinking budget is drawn from `max_tokens` rather than added to it. None of that was reachable
from a dry run, because the mock accepted any schema handed to it. It now enforces the same rules
— a rehearsal is worth only what it validates.

**Thresholds were frozen before any of it ran** (ADR-0003, `eval/preregistration.lock.json`). The
lock hashes the thresholds together with the prompt registry, tool registry, policy bundle and
corpus manifest. The runner refuses to produce a reportable result if any of them drifted, because
a threshold reinterpreted after seeing results is a description of the data.

The adversarial suite found three real gaps in this codebase within an hour of existing: scope
enforced only inside the planner (a check a compromised planner simply does not run), approval
decided by policy alone while the trusted registry's `requires_approval` was ignored, and nothing
stopping an agent reading credentials inside its own assigned repository. All three are fixed and
have regression tests.

## Architecture

```
untrusted context ──► LangGraph planner ──ActionPlan──► OPA policy ──► capability minter
(repo, Jira,          (reasons, cannot                  (decides)      (Ed25519, scoped)
 scanners, tags)       execute)                                              │
                                                                             ▼
                                                                      MCP Gateway
                                                                    (sole dispatch path)
                                                                             │
                                        ┌────────────────────────────────────┤
                                        ▼                                    ▼
                              private stdio MCP servers            Docker sandbox
                                                                (no network, non-root)
```

Durability, retries, cancellation and human-approval waits are owned by Temporal. Workflow code
performs no I/O — all of it lives in activities.

Full trust boundaries and adversary model: [`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md).

## Getting started

**Requirements:** Python 3.12+, [uv](https://docs.astral.sh/uv/), Docker with Linux containers.
`make` is *not* required.

```bash
# 1. Keep the virtualenv out of any synced folder (OneDrive, Dropbox, ...)
export UV_PROJECT_ENVIRONMENT="$HOME/.venvs/agentsec"      # PowerShell: $env:UV_PROJECT_ENVIRONMENT

# 2. Install
uv sync --group dev

# 3. Verify the environment before doing anything else
pwsh -File scripts/preflight.ps1        # Windows
uv run task validate-package            # any platform

# 4. Run the checks
uv run task check                       # lint + format + typecheck + tests
```

### Tasks

| Command | Does |
|---|---|
| `uv run task check` | lint, format check, typecheck, tests |
| `uv run task lint` / `task format` | ruff |
| `uv run task typecheck` | mypy strict |
| `uv run task test` | pytest |
| `uv run task validate-package` | verify the execution backlog is internally consistent |

### A note on Windows

Development happens on Windows 11 with Docker Desktop / WSL2. Two consequences worth knowing:

- WSL2 defaults to half the host's RAM and every logical processor. `scripts/preflight.ps1 -Fix`
  writes a `~/.wslconfig` capping it. Run `wsl --shutdown` to apply.
- If the repository sits in a synced folder, never bind-mount it into a container. Sandbox
  workspaces stage into per-run Docker volumes instead — which is better isolation regardless.

## Observability

The audit trail is designed to be checked *without* the code that wrote it.

```bash
uv run task replay eval/runs/<run-id>/events.jsonl        # timeline + verdict
uv run task replay eval/runs/<run-id>/events.jsonl --metrics
docker compose --profile observability up -d              # Prometheus + Grafana
```

Two series carry the argument, and they are shown side by side on purpose:

| Series | Expected |
|---|---|
| `agentsec_unauthorized_attempts_total` | large |
| `agentsec_unauthorized_executions_total` | zero |
| `agentsec_replay_violations_total` | zero |
| `agentsec_policy_fail_closed_total` | watched — a dead policy engine denies everything and produces a run that looks perfect |

A dashboard showing only the executions panel looks identical whether the controls are working or
the agent is idle.

## Scanners

Semgrep and Trivy run as digest-pinned containers inside the AS-031A sandbox: no network,
no capabilities, a read-only root filesystem, a non-root user, and a per-run volume that
is never a bind mount of the host. Neither adapter accepts a command, an argument list or
a flags string — a caller picks an enumerated mode and a validated path, and nothing else
reaches the process. That is enforced by a test over the adapters' signatures, not by
review.

**Semgrep rules here are first-party.** `policy/semgrep/agentsec.yaml`, written for this
project's fixture corpus, rather than anything from Semgrep's registry. Two reasons:

- *Licensing.* The community rules are under the Semgrep Rules License v1.0, limited to
  internal, non-competing use — the term that prompted the [Opengrep](https://opengrep.dev)
  fork. Vendoring them into a public repository is not defensible. **Opengrep is a drop-in
  replacement** for anyone who wants registry-equivalent coverage; swap the image pin in
  `src/agentsec/images.py`.
- *Determinism.* The evaluation compares detections against known ground truth. A pinned
  first-party ruleset gives a fixed denominator; a drifting upstream registry means last
  month's numbers cannot be reproduced.

**Trivy's vulnerability database is fetched once and then never touched.** Trivy ships
without one and downloads it on first run, which would make every scan depend on the day
it ran. Exactly one operation touches the network — `TrivyScanner.ensure_database()` —
and every scan afterwards runs with `--network none`, `--skip-db-update`,
`--skip-java-db-update` and `--offline-scan` against a read-only cache. The database
version travels on every result, so an artifact says which one produced it.

docs/adr/                   architecture decision records

src/agentsec/               implementation

(CSV, summary, dependency graph, manifest) are generated from the issue files and verified to be a
